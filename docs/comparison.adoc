= CORE-V-Wally Compared with Other RISC-V Cores

These tables compare CORE-V-Wally configurations with other open-source cores that have
https://github.com/riscv/riscv-arch-test[riscv-arch-test] (ACT) configurations.
Each row describes the configuration ACT builds, at the core commit ACT pins; the core name links to that commit.
Areas do not include L2 caches or tightly coupled memories (ICCM, DCCM, IROM, DTIM): they cover the core and its L1 caches,
as CORE-V-Wally's own results do.
See the <<_reproducing_the_tables,last section>> for where each entry comes from.

This comparison attempts to show each core in its most positive light: each runs the configuration and build its developers
chose for riscv-arch-test, with the most favorable settings we found (footnoted). If a core is not configured well here,
please https://github.com/openhwfoundation/cvw/issues[file an issue].

The data in these tables were collected with the help of AI (Claude Code): runs were scripted and checked, and descriptions,
readiness levels, and documentation ratings were researched from the cited sources, but errors are possible.
Corrections are appreciated, as an issue or a pull request.

For Verilog, SystemVerilog, and VHDL cores, the list is the files whose modules the core's riscv-arch-test simulation elaborates under the core's top, with the packages and headers they use (from the same Verilator command with `--xml-only` or `--json-only`, or from ghdl for VHDL), rather than the whole file list, which can compile unused alternatives. == Reproducing the Tables

The privilege modes and extensions are the `implemented_extensions` of each configuration's
https://github.com/riscv/riscv-unified-db[UDB] architecture yaml in riscv-arch-test, at
https://github.com/riscv/riscv-arch-test/tree/cbbb9f0eb59beb5588e9158a7c13aace48231c51[act4 cbbb9f0eb] or in the open pull request listed below.
U, S, and H appear as privilege modes; M implies Zmmul, A implies Zaamo and Zalrsc, C implies Zca and its F and D
variants, and B stands for Zba, Zbb, and Zbs.
The other rows summarize each core's documentation and RTL at the commit ACT pins in
`.github/scripts/install-<core>.sh`, for the build parameters that script and the configuration's `run_cmd.txt` use.
The CORE-V-Wally entries come from the link:../README.md#configurations[Configurations table] in the README.

=== Synthesis

Every core is synthesized with CORE-V-Wally's `synthDC` flow: Design Compiler Y-2026.03-SP3 in topographical mode with TSMC 28HPC+ TT
libraries (0.9 V, 25 °C) and TLU+ parasitics, so timing and area include wire delays.
The area covers the core and its L1 caches. L2 caches and tightly coupled memories (VeeR ICCM and DCCM, CORE-V-Wally IROM and DTIM)
are not included; CORE-V-Wally's microcontroller configurations are synthesized with the AHB bus in their place.
Small, multi-ported, or associative arrays (register files, TLBs, queues, small predictor tables) are synthesized as flip-flops.
Large one- and two-port arrays (cache data and tags, large predictor tables) are SRAM macros; Logic Area excludes them,
Total Area includes them, and RAM Bits is their capacity.
CORE-V-Wally instantiates macros generated with the TSMC 28HPC+ memory compilers.
For the other cores, each such array is an estimated macro of exactly its size: its area, access time, setup times, and cycle
time come from the TSMC 28HPC+ memory compilers' quick-reference tables at the same corner (SVT periphery), interpolated
between table entries, with the timing tables and pins of a generated macro of the same kind. The quick-reference tables
reproduce the generated macros' timing to within 1 ps and overstate their area by 5%, so the estimated areas are scaled by 0.95
(0.97 for dual-port macros); the two-port register-file compiler has no generated macro to compare against, so its areas are
not scaled. The clock frequency is also limited by each macro's minimum cycle time.

=== Embench

Embench speed runs on the same testbenches with the common build in link:../benchmarks/comparison/README.md[benchmarks/comparison]:
the flags of CORE-V-Wally's Embench speed build (`-O3 -flto -funroll-loops`, plus `-fwrapv` on RV32), no F or D on any core
(so the floating-point benchmarks use software floating point), riscv64-unknown-elf-gcc 15.2.0 for RV32, and a medany GCC 16.1.0
toolchain for RV64. The score is the geometric mean over the 22 benchmarks of Embench's baseline time divided by the measured
cycles at 1 MHz, as Embench's `benchmark_speed.py` computes it, and a benchmark counts only if its own check passes.

export ACT_CONFIGS=... CI_TOOLS=... RV64_TOOLCHAIN=<bin directory of a medany riscv64-unknown-elf toolchain>

----

=== CoreMark

CoreMark runs on each core's riscv-arch-test testbench with link:../benchmarks/coremark[CORE-V-Wally's CoreMark port],
which link:../benchmarks/comparison/README.md[benchmarks/comparison] documents:

* The program boots, halts, and prints with the configuration's `rvmodel_macros.h` and links with its `link.ld`.
* Time is `mcycle` (or the noted substitute), and CoreMark/MHz = Iterations × 10^6^ / Total ticks, with 10 iterations unless noted.
  A result counts only if CoreMark reports "Correct operation validated".
* Every core is compiled with riscv64-unknown-elf-gcc 15.2.0 and CORE-V-Wally's CoreMark flags,
  for its subset of IMAFDC, Zba, Zbb, Zbs, and Zbc; other extensions such as Zcb, Zicond, scalar crypto, and V are not used.
* `ee_u32` is `signed int` on RV64, as in CORE-V-Wally's and SiFive's RV64 ports, and `unsigned int` on RV32.
* Core-specific steps, each footnoted in the table, are behind compile flags of the port.
* CoreMark IPC is the instructions retired in the timed region (`minstret`, with `-DCOUNT_INSTRET`) divided by its cycles.
  Cores built for the same ISA execute identical instruction counts there: 238,965 per iteration for RV32IMC, 203,014 with B and Zbc,
  247,612 for RV32EMC, 210,696 for RV64IMAFDC with B and Zbc, 243,700 with B but not Zbc, and 247,606 without B.

----
export ACT_CONFIGS=<directory of ACT configuration directories> CI_TOOLS=<directory of ACT core installs>
benchmarks/comparison/coremark/run_all.sh            # all cores, or name the ones to run
----
